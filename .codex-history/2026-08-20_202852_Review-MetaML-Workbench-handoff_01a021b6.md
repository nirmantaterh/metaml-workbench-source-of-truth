What I understand is:

- The architecture is split into a Workbench front end, a `wbapi` Spring Boot host, a `workbench` domain/generation module, and a generated Target Platform that runs as its own child JVM. The generated app has its own API and dashboard, separate from the Workbench UI.
- There are two different twin concepts and they must stay separate:
  - Governance/Evolve shadow twin: `TwinModelGenerator`
  - Operational runtime twin: `OperationalTwinGenerator`
- The current generation flow is: save BPMN in the Workbench, generate a standalone app, optionally derive an operational Twin automatically when the Main BPMN has the matching signal-gated shape, then launch the generated app and open its own URL.
- The generated Target Platform is not a Workbench route. It is a separate app with `/api/v1/platform/info`, `/api/v1/platform/recent-instances`, and `/api/v1/platform/start/{processDefinitionKey}`, plus the static dashboard at `/`.

What is already completed and present in the repo:

- BPMN modeling, save/load, persistence, archive history, generation, and launch all exist.
- Automatic operational Twin derivation is wired in before the normal generation path.
- The authored/manual Twin path still exists and still takes precedence when a Twin BPMN is attached.
- The Workbench UI has `Open Target Platform` behavior on both the model page and deployed-apps page.
- The generated Target Platform dashboard currently shows deployed processes, activity names, active instance counts, RabbitMQ status, recent runtime activity, and process variables for each instance.

What I see as the current limitations and scope boundaries:

- The operational Twin generator is pattern-based. It derives a Twin from Main whenever it sees the current catch-event + external-task gate shape, and it cannot perfectly tell intended Twin-facing gates from similar Main-only gates. The RedCollar fixture therefore produces a superset Twin that includes `Verify Order Details`.
- The Target Platform UI is currently generic runtime introspection plus process-variable display. It does not yet have a dedicated order list or richer business-data UI.
- The repo’s own docs and tests already treat those as open questions rather than implemented requirements.

The two requirements still awaiting Joanna’s clarification are:

- Whether operational Twins should be auto-generated for every BPMN matching the current pattern, or only in a narrower/explicitly requested scope.
